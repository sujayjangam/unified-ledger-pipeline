# Splits — plan

> **Status: planned 2026-11-16. PR 1 written 2026-11-16 (ADR-0039, ADR-0040); PRs 2 and 3 not started.** Step 3 of group-trip splitting in `ROADMAP.md`.
> Names below are fictional.

## Goal

Record who shares each entry and how much each person's share is, so step 4 (`/balances`) can
work out who owes whom. The person logging says it in plain words and never does the maths. The
card arrives already filled in; buttons are for fixing it, not for building it.

## Decided (2026-11-16)

1. **The message decides, not trip mode.** An entry is split only when the message asks for it
   ("split", "shared", "between", and the like). A message that says nothing about splitting is a
   personal entry, with trip mode on or off.
2. **The model reads the split; Python works it out.** The model returns only who and how many:
   people, families, "everyone", "except", nights, a fixed amount. It never returns a share.
   Python matches the names and hands out the cents, the way dates work
   ([ADR-0030](../../decisions/0030-llm-reads-dates-python-resolves.md)).
3. **The card shows every share before Confirm.** A misread split is never silent.
4. **"With" includes the sender; "between" doesn't.** "Split with Carol" is the sender and Carol.
   "Split between Carol and Dave" is only those two; the sender has no share.
5. **Who can be named.** While trip mode is on, only that trip's members. While it is off, every
   participant, so a friend added for a past trip can share an everyday bill.
6. **"Everyone" needs a trip.** With trip mode on it means the trip's members. With it off the bot
   refuses to guess: the card warns, and the split menu opens with nobody ticked.
7. **The split menu opens with everyone ticked** when the message gave no split to start from
   (trip mode on). Spliit, read 2026-11-16, starts a new expense the same way: every group member,
   even shares.
8. **The model becomes a second reader for the payer.** Python's patterns
   ([ADR-0037](../../decisions/0037-paid-by-person-read-from-text.md)) miss phrasings such as
   "Carol covered dinner", and the card then shows the sender with no warning. So:
   - Python's pattern matches: Python wins, and the model's answer is ignored.
   - Python finds nothing and the model names a known person other than the sender: that person is
     used, and the card says "⚠️ Read as: Carol paid. Check."
   - Otherwise the sender paid, as today.

   This changes part of ADR-0037 and gets its own record.

Also decided 2026-11-16:

- **Leftover cents.** Each share is rounded down, then the spare cents go one each to the people
  with the largest remainder; ties go to the lowest participant id. The same entry always splits
  the same way. The payer gets no special treatment: they may not be in the split at all.
  (`ROADMAP.md` suggested "whoever's card paid"; this replaces it for that reason.)
- **A name that doesn't match.** The people who did match keep their shares, the card shows
  "⚠️ Couldn't match 'Zed'", and the menu fixes it. Nobody is guessed.
- **Totals.** Today `/today`, `/week`, `/month` and the category views count an entry in full, or
  not at all when an outside person paid. Once shares exist they should count the household's
  shares of a split entry, whoever paid. That change lands in step 4, with `/balances`, not here.
- **Refunds.** Out of scope: the bot rejects a negative amount today.

## Design

**Migration 0008** (hand-written, additive): `transaction_splits`
- `transaction_id` → `transactions.transaction_id`, `ON DELETE CASCADE`
- `participant_id` → `participants.id`
- `share_cents BIGINT NOT NULL`, `>= 0`
- primary key (`transaction_id`, `participant_id`)

No rows means "not split": the entry is the payer's alone. Shares must add up to the entry's
amount. That is checked in Python before the insert and written in the same database transaction
as the entry, only when the entry row was really inserted (the idempotency key still decides).

**The cents (pure Python, `app/services/splits.py`).**
`share_out(amount_cents, weights)` takes a weight per person and returns whole cents per person
that add up exactly. An even split is every weight 1. A fixed amount ("Carol's share is 50") is
taken off first, and the rest is shared out by weight. Tested without a database or the model.

**What the model returns.** A `split_reference` on each transaction, like `date_reference`:
- `kind`: `none`, `everyone` or `named`
- `include_sender`: true for "with", false for "between"
- `people`: names as said, each marked person or family ("Carol's family")
- `except_people`: names as said
- later (PR 3): a count per name (nights), a fixed amount per name

And one more field, `payer_name`: the person the message says paid, copied as said, or null.

**Matching names (Python).** The same rule as `read_payer`: a whole display name, or one word of
it nobody else on the list shares. A family is everyone with the same `trip_members.family` as
the person named; with trip mode off there are no families, only people.

**The card** gains one line per person under "Paid by", grouped by family while a trip is on, and
keeps its warnings as lines that never block a save.

**The split menu** (PR 2) reuses `_people_keyboard`: one row per family with an "all of this
family" toggle, a tap to toggle a person, and Done. It runs inside the card's lock and changes
only the pending entry ([ADR-0038](../../decisions/0038-paid-by-button-starts-from-the-message.md)).

## Risks to test

- The model invents a split that wasn't asked for, or misses one. Measured with
  `scripts/check_extraction` before merging. If it invents them, add a Python check that the
  message contains a split word, as "last week" is checked
  ([ADR-0031](../../decisions/0031-last-week-from-message-text.md)).
- The model reads "split with Carol" as "Carol paid". Trap cases go in `check_extraction`. If it
  swaps them often, the second reader only warns ("⚠️ Did Carol pay?") and the sender stays.
- Ten people's shares on one card: the card must stay readable on a phone.
- A name that is also an everyday word, as for the payer.

## Steps

Three PRs, in this order, so the trip has a usable minimum after the second.

**PR 1: read, store, show.**
1. ADRs: splits read by the model and worked out by Python; the model as second reader for the
   payer.
2. Migration 0008 on a Neon branch; `docs/SCHEMA.md`.
3. `share_out`, with tests for leftover cents and for sums.
4. `split_reference` and `payer_name` in `app/services/extraction.py`; the five messages in
   `ROADMAP.md` step 3 and the payer traps added to `scripts/check_extraction`, then run.
5. Name matching and split resolving in `process_expense_text`; the second-reader payer rule.
   Even splits only: people, families, everyone, except.
6. Share lines on the card; saving the shares with the entry.
7. Gate, test bot on the Neon branch, production migration by hand, merge.

**PR 2: the split menu.** "Add split" / "Change split" button, the family rows, Done. Opens with
what was read, or everyone ticked.

**PR 3: uneven shares.** Nights or any count per person, and a fixed amount with the rest shared.
The model fields, the maths (already general) and the card wording.

## Testing on a past trip

A replay script reads a gitignored CSV of a finished trip (amount, currency, who paid, who
shares, weights) and runs it through `share_out` and the step 4 balances function. No bot, no
model, no database, so it costs nothing. It lands with step 4. The awkward entries can also be
typed into the test bot with that trip seeded on the Neon branch, which tests the reading too.

## Out of scope

`/balances` and settlement (steps 4 and 5), refunds, more than one payer per entry, FX conversion.
